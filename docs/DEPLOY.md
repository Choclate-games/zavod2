# Фабрика на мини-ПК: контейнер, вход, автодеплой

Рабочий ПК запускает фабрику локально (`python run_web.py`). На мини-ПК она
живёт иначе: в контейнере, за паролем и с автообновлением из `main`.

Этот документ — про второй случай.

## Что где

| | |
|---|---|
| Машина | мини-ПК `192.168.1.194`, пользователь `oem` (uid 29999) |
| Лимиты фабрики | 5 ГБ памяти, 3 ядра (из 7,5 ГБ и 4 ядер машины) |
| Каталог | `/opt/zavod2` — обычный клон этого репозитория |
| Сайт из дома | `http://192.168.1.194:7860` |
| Сайт из VPN | `http://172.29.172.1:8080` |
| Контейнеры | `zavod2-factory`, `zavod2-runner` |
| Архивы игр | `/opt/zavod2/builds/` + таблица `builds` в MySQL |
| Раннер | `minipc-zavod2`, метка `zavod2`, привязан к репозиторию |

Раннеры организации (`gh-runner-1`, `gh-runner-unity-1`) живут в другом
compose и про этот не знают: другие метки, другие контейнеры, другие тома.

## Вход

Фабрика запускает терминальных агентов и выполняет сгенерированный ими код.
Открытый интерфейс — это удалённое выполнение кода на машине, где рядом
работают раннеры организации, поэтому вход обязателен и включён по умолчанию.

Пароль хранится хешем, сессия — в подписанной куке:

```bash
python -m app.web.auth --hash    # спросит пароль, напечатает строку для .env
```

Строка кладётся в `AUTH_PASSWORD_HASH`. Смена пароля автоматически
разлогинивает все открытые сессии: ключ подписи кук выводится из самого хеша.

Пароль при этом живёт в двух местах, и это не дублирование ради симметрии.
Действующий хеш лежит в таблице `users` — только так его можно поменять из
интерфейса, не заходя по ssh. Копия остаётся в `.env`, потому что база стоит
на чужом хостинге: если единственная копия хеша там, недоступность Beget
означает невозможность войти в фабрику на собственной машине.

Смена пароля из интерфейса — «Настройки → 🔐 Доступ». Действует немедленно,
перезапуск контейнера не нужен: `AUTH` меняется на месте, а middleware читает
его на каждом запросе.

Отключается только для локального запуска на `127.0.0.1` — `AUTH_ENABLED=0`.
В контейнере это невозможно: `compose.yml` навязывает `AUTH_ENABLED=1` поверх
`.env`. При `AUTH_ENABLED=1` и пустом хеше сервер не поднимется вовсе — лучше
не запуститься, чем запуститься открытым.

Защита от перебора: десять неудачных попыток с одного адреса за пятнадцать
минут, дальше `429`. Счётчик в памяти, рестарт его обнуляет.

### Про `$` в `.env`

Docker Compose разворачивает `$` в значениях `env_file`. Если доллар окажется
внутри ключа, до контейнера доедет обрезанная строка, а compose ограничится
предупреждением `variable is not set`. Экранируется удвоением: `$$`.

Хеш пароля от этого защищён — в нём двоеточия, ровно по этой причине.

## Два файла с настройками

| Файл | Кому виден | Что внутри |
|---|---|---|
| `.env` | контейнеру фабрики | ключи провайдеров, пути, настройки входа |
| `.env.deploy` | контейнеру раннера | `GITHUB_REPO`, `GITHUB_PAT`, имя и метки раннера |

Разделение не косметическое. `.env` уезжает в фабрику целиком, а внутри неё
выполняется сгенерированный агентами код — токена с правами на запись в
репозитории организации там быть не должно.

На мини-ПК в `.env` переопределены пути (`/app/workspace`, `/app/output`
вместо путей Windows), выключены уведомления и задан `PREVIEW_HOST`.

## Как работает автообновление

```
push в main
   │
   ▼
workflow Deploy  →  раннер zavod2  →  тесты (389 шт.)
                                   →  самопроверка входа
                                   →  трогает /deploy/trigger
                                            │
                                            ▼
                              systemd zavod2-deploy.path (на хосте)
                                            │
                                            ▼
                              docker/deploy.sh: git merge --ff-only
                                               docker compose build factory
                                               docker compose up -d factory
```

Раннеру **не даётся** `/var/run/docker.sock`. Он не умеет ни собирать образы,
ни перезапускать контейнеры — только тронуть файл в bind-монте. Всё остальное
делает systemd от имени `oem`. Это сохраняет правило CI-инфраструктуры мини-ПК:
код из workflow не управляет демоном Docker хоста.

Несколько отдельных решений, каждое со своей причиной:

* **Регистрация на уровне репозитория, а не организации.** Org-раннер доступен
  всем репозиториям организации — job из любого из них выполнялся бы здесь.
* **Триггер только `push` в `main`.** Репозиторий публичный. `pull_request`
  означал бы выполнение кода с чужого форка на домашней машине.
* **`paths-ignore` на `workspace/` и `output/`.** Сгенерированные игры едут в
  git вместе с кодом, то есть коммит очередной игры — тоже push в `main`.
  Без фильтра фабрика перезапускала бы сама себя посреди работы.
* **`git merge --ff-only`, а не `reset --hard`.** В `workspace/` могут лежать
  ещё не закоммиченные игры. Деплой скорее встанет с внятной ошибкой, чем
  сотрёт их.
* **Деплой не трогает контейнер раннера.** Его перезапуск убил бы job, который
  этот самый деплой и запустил. Раннер обновляется руками:
  `docker compose up -d --build runner`.
* **После сборки скрипт сам перепроверяет `origin/main`.** У связки
  «`.path` с `PathModified` + `oneshot`» есть щель: пока сервис деплоя
  работает, юнит пути деактивирован, и запись в файл-триггер, случившаяся в
  этот момент, до systemd не доходит. Два пуша подряд — и второй теряется
  молча, с зелёной галочкой в GitHub. Проверено на себе. Поэтому `deploy.sh`
  крутит до трёх кругов, пока рабочая копия не сравняется с `origin/main`, а
  на занятом локе ждёт, а не выходит.

## Node в образе

Версия зафиксирована тегом: `node:22-bookworm-slim`. Не 20 — фабрика ставит в
общий стор `pnpm@latest`, а pnpm 10 требует Node >= 22.13 и импортирует
встроенный `node:sqlite` (появился в 22.5). На Node 20 он падал с
`ERR_UNKNOWN_BUILTIN_MODULE`, и вместе с ним падал **каждый** `npm install`
сгенерированной игры: привычные команды заворачиваются в pnpm через shim из
`app/pkgstore.py`.

Отката при этом не было: фабрика уходила на обычный npm, только если pnpm не
удалось *установить*, а не если установленный не *работает*. Теперь
`find_pnpm()` проверяет `pnpm --version` (один раз на процесс) и при неудаче
возвращает None, а `ensure_pnpm()` переставляет сломанный. Так следующее
расхождение версий обойдётся замедлением, а не остановкой.

## Что переживает пересборку

| Что | Где лежит |
|---|---|
| Игры (`workspace/`, `output/`, `zip_projects/`) | bind-монт в рабочую копию — оттуда же их забирает git |
| Архивы после прогонов (`builds/`) | bind-монт в рабочую копию |
| Общий стор node-пакетов (`.pkgstore/`) | bind-монт в рабочую копию |
| Авторизация всех шести агентов | том `factory-home` (`/home/factory`) |
| История расхода и квот | том `factory-state` (`/app/state`) |

Стор пакетов — bind-монт, а не именованный том, и это не вкусовщина. pnpm
раскладывает `node_modules` игр жёсткими ссылками на файлы стора, а жёсткая
ссылка через границу файловой системы невозможна: с томом pnpm молча свалился
бы на копирование, и весь смысл общего стора исчез бы. `workspace/` приезжает
с того же `/opt/zavod2`, поэтому ссылки остаются в пределах одного устройства.

До этого стор жил в слое образа и умирал на каждом деплое — следующая сборка
любой игры заново качала полсотни мегабайт и переставляла pnpm.

История квот заслуживает пояснения. Модули `providers/agent_usage.py`,
`providers/agy.py` и `providers/quota_probe.py` ищут её по путям рядом с кодом:

```python
Path(__file__).resolve().parent.parent / ".agy_quota_history.json"
```

Путь захардкожен, переменной окружения нет — в контейнере это слой образа, и
история обнулялась бы на каждом деплое. `docker/entrypoint.sh` уводит эти
файлы симлинками в том. Работает потому, что все три модуля пишут через
`open(path, "w")`, то есть в существующий файл по ссылке.

## Авторизация агентов

Ставится один раз, живёт в томе `factory-home` и переживает пересборку.

Обычный путь — «Настройки → ⌨️ Вход в агентов»: терминал прямо в браузере,
кнопка на каждого агента. Подробности ниже, в разделе про терминалы.

Через ssh, если интерфейс почему-то недоступен:

```bash
docker compose exec factory claude      # дальше по ссылке в браузере
docker compose exec factory codex
docker compose exec factory opencode
docker compose exec factory agy
```

## Предпросмотр игр

`app/game_runner.py` поднимает dev-сервер игры и отдаёт браузеру адрес. На
одной машине это `localhost`; на сервере — нет, потому что «localhost» в
браузере пользователя это его собственный компьютер.

Поэтому адрес прослушивания и адрес для браузера разведены:

Диапазон портов — не украшение: наружу из контейнера опубликованы именно
`5100-5109`, и туннель пробрасывает именно их. Порт вне диапазона снаружи не
открывается вообще.

Здесь была ошибка, стоившая всего предпросмотра. Фабрика запускала
`pnpm run dev -- --port 5100 --strictPort`, а pnpm передаёт `--` дальше
буквально: до vite доезжало `vite -- --host 0.0.0.0 --port 5100`, и cac считал
всё после `--` сырыми аргументами. Vite садился на свой 5173, браузер получал
адрес, который не открывается, — при полностью живом сервере. npm при этом
`--` требует. Теперь разделитель подставляется по менеджеру
(`game_runner._script_args`).

| Переменная | На мини-ПК | Зачем |
|---|---|---|
| `PREVIEW_BIND` | `0.0.0.0` | где слушает vite внутри контейнера |
| `PREVIEW_HOST` | `172.29.172.1` | что подставляется в ссылку (адрес туннеля — работает и из дома, и из VPN) |
| `PREVIEW_PORT_MIN/MAX` | `5100`/`5109` | контейнер публикует только заранее заданные порты |

При локальном запуске переменные не заданы и поведение прежнее.

**Важно:** dev-серверы игр за формой входа не стоят — это отдельные процессы
vite на своих портах. Снаружи они видны только через туннель, то есть тем, у
кого поднят VPN, но не отдельным паролем. Если нужно жёстче — правила на
`awg0` внутри контейнера AmneziaWG на VPS.

## Доступ из VPN

Из домашней сети сайт открывается напрямую по `192.168.1.194:7860`. Снаружи —
с телефона, ноутбука, откуда угодно, где поднят твой VPN — по адресу
`http://172.29.172.1:8080`.

Почему нельзя было просто «дать доступ к мини-ПК». На сервере AmneziaWG все
пиры объявлены как `/32`, домашняя сеть за роутером не анонсируется. Пакет от
пира `10.8.1.x` на `192.168.1.194` сервер выбрасывает: он не знает, за каким
пиром живёт эта сеть. Роутер выпускает LAN наружу, но внутрь дороги нет.

Сделано обратным SSH-туннелем: мини-ПК сам держит соединение до VPS и
публикует на нём порты.

```
телефон 10.8.1.x
   │  http://172.29.172.1:8080
VPS: контейнер amnezia-awg2 ──FORWARD──> мост amn0 (172.29.172.1)
                                             │  sshd, порт открыт только здесь
   ssh -R (исходящее соединение) ────────────┘
мини-ПК: uvicorn на 127.0.0.1:7860
```

Ключевое: `172.29.172.1` — это мост docker внутри VPS. На публичном `ens1`
порт не слушается вообще, поэтому из интернета сайт недоступен в принципе, без
единого правила фаервола. Проверено: `curl 195.26.230.225:8080` соединения не
даёт.

Адрес работает одинаково и для пиров VPN, и для домашних машин, чей трафик
роутер заворачивает в туннель.

### Почему туннель, а не пир WireGuard на мини-ПК

Отдельный пир дал бы адрес поприятнее (`10.8.1.9`) и сохранял бы исходные IP
клиентов. Но у мини-ПК **нет учётки в VPN**: в `~/.config/AmneziaVPN.ORG/`
лежат адрес сервера и параметры обфускации, а ключей и выданного адреса нет.
Завести их пришлось бы правкой `awg0.conf` внутри контейнера — файла, который
переписывает приложение Amnezia при каждом добавлении клиента. Туннель не
зависит ни от конфигурации сервера VPN, ни от роутера и вообще не трогает сеть
мини-ПК, то есть не может задеть раннеры организации на этой же машине.

Динамический домашний IP роли не играет: соединение инициируется изнутри.

### Что настроено

На VPS — пользователь `tunnel` (`nologin`, ключ с `restrict,port-forwarding`:
сессию открыть нельзя, только проброс) и drop-in
`/etc/ssh/sshd_config.d/60-zavod2-tunnel.conf`:

* `GatewayPorts clientspecified` — иначе `-R` умеет биндить только `127.0.0.1`.
* `ClientAliveInterval 30` — вот это про динамический IP. При его смене TCP
  умирает молча, а sshd держит порт занятым; переподключение упирается в
  «address already in use», и сайт пропадает до ручного вмешательства.

На мини-ПК — `zavod2-tunnel.service` с `Restart=always` и
`ExitOnForwardFailure=yes`. Второй флаг обязателен: без него ssh при занятом
порте остаётся жив и молча ничего не пробрасывает — systemd считает, что всё в
порядке, а сайта нет. Проверено убийством процесса: туннель поднимается сам за
десяток секунд.

Кроме сайта пробрасываются порты `5100-5109` — dev-серверы игр. Без них с
телефона открывался бы интерфейс, но не запущенная игра. По этой же причине
`PREVIEW_HOST=172.29.172.1`.

## MySQL

База — на шаред-хостинге Beget, `mrnuryn3.beget.tech`. Реквизиты в `.env`
(`MYSQL_*`), схема создаётся сама при первом подключении.

Что где лежит:

| Таблица | Что в ней |
|---|---|
| `users` | вход в фабрику |
| `projects` | реестр витрины: оценка, архив, избранное, название |
| `builds` + `build_chunks` | журнал zip-архивов; содержимое — зеркало живых игр и копии убранных в архив |

Что **не** переехало: сами игры, чаты, снимки отката, история расхода токенов.
Причина одна и измеримая — запрос до Beget занимает около ста миллисекунд.
Витрина из полусотни игр, читающая метаданные по одной записи, открывалась бы
пять секунд. Поэтому реестр целиком читается одним запросом раз в минуту и
живёт в памяти, а запись идёт сразу и в базу, и в локальный JSON.

Недоступность базы фабрику не роняет: `app/db.py` отдаёт `available() == False`,
и `app/project_meta.py` работает по JSON ровно как до переезда.

### Доступ по IP

Beget выдаёт права на конкретный адрес:

```
GRANT ALL PRIVILEGES ON `mrnuryn3_zavod`.* TO 'mrnuryn3_zavod'@'195.26.230.225'
```

`195.26.230.225` — это VPS. Мини-ПК ходит в интернет через него, пока роутер
заворачивает его трафик в VPN, — но набор устройств в политике PBR хранится в
volatile-множестве nftables и сбрасывается на каждом `fw4 reload` (это записано
в `logRouter/etc/nftables.d/10-custom-filter-chains.nft`). После сброса мини-ПК
уходит в интернет с домашнего динамического адреса, и база отваливается — молча,
потому что фабрика просто переключается на JSON.

Поэтому подключение к MySQL идёт **через тот же обратный туннель**, что и сайт:
в `zavod2-tunnel.service` добавлен локальный проброс

```
-L 172.17.0.1:13306:mrnuryn3.beget.tech:3306
```

Соединение к Beget при этом инициирует VPS, то есть адрес источника всегда
`195.26.230.225`, независимо от роутера. Контейнер ходит на `172.17.0.1:13306`
(мост docker хоста) — адрес указан в `.env` мини-ПК.

Задержка запроса с мини-ПК — около **410 мс** (с рабочего ПК вдвое меньше:
короче путь). Туннель её не добавляет — он её стабилизирует: напрямую разброс
был 312–712 мс, через готовое ssh-соединение стабильно 410.

Ещё одно следствие этой задержки: после неудачного подключения фабрика не
трогает базу полминуты (`FAILURE_COOLDOWN_SECONDS`). Иначе при мёртвом
хостинге каждый вызов упирался бы в `connect_timeout`, и постановка оценки в
витрине висла бы по десять секунд — на каждый клик.

Две особенности сервера, которые учтены в коде:

* `wait_timeout` = **30 секунд**. Соединение, полежавшее без дела полминуты,
  сервер закрывает молча, а установка нового занимает почти две секунды.
  Поэтому пул пингует простаивающие соединения раз в двадцать секунд.
* `STORED` — зарезервированное слово MySQL 8. Колонка, где отмечено наличие
  копии архива в базе, называется `in_db` именно поэтому.

### Часы

Их тут трое, и все идут по-разному.

Beget отстаёт от местного времени на два часа, поэтому фабрика датирует записи
своими часами, а не `NOW()`: иначе архив, снятый в 23:06, значился бы снятым в
21:06 — расходясь с меткой в имени того же самого файла.

Но «свои часы» контейнера по умолчанию UTC, то есть на пять часов позади
мини-ПК. Поэтому в `compose.yml` задан `TZ` (`Asia/Yekaterinburg`, переопределяется
в `.env`). Без него имена автоархивов, метки чатов и даты в реестре расходились
бы с часами на экране — молча и на пять часов.

### Зеркало живых проектов

Холодные архивы закрывают один случай: игра, убранная с диска, существует хотя
бы где-то. Но игра, лежащая на диске, пропадает вместе с диском — а мини-ПК это
один SSD без RAID, и игры, сделанные прямо на нём, в git не уезжают (фабрика не
коммитит).

Поэтому раз в час фабрика сверяет каждую живую игру с её копией в базе и
обновляет копию, если на диске появилось что-то новее:

```
поток mysql-mirror (час)
   │
   ├── занята агентом? → пропустить (слепок с середины работы — не версия игры)
   ├── время правок <= времени копии? → пропустить
   ├── есть готовый архив в builds/ новее правок? → залить его, не паковать заново
   └── иначе упаковать и залить, старую копию убрать
```

Время правок считается по исходникам: `node_modules` и прочее восстановимое из
обхода исключены, иначе `npm install` выглядел бы как правка игры.

Копия на игру ровно одна. Бюджет (`MYSQL_MIRROR_BUDGET_MB`, по умолчанию 512)
останавливает приём **новых** игр, но не мешает обновлять уже взятые:
замороженная копия месячной давности хуже её отсутствия, потому что выглядит
как резервная.

Кнопка «☁ Сверить с базой» в «Настройки → Хранилище» запускает тот же обход
руками.

## Терминалы CLI-агентов

«Настройки → ⌨️ Вход в агентов» — настоящий терминал в браузере: PTY на сервере,
xterm.js на клиенте, обмен по вебсокету.

Понадобилось потому, что вход в claude, codex, opencode и agy интерактивный: CLI
рисует меню и ждёт вставленный код. Прежняя кнопка «Открыть терминал» открывала
окно на машине, где идёт процесс, — на мини-ПК открывать нечего.

Через пайпы это не работает в принципе: CLI проверяют `isatty()` и без терминала
уходят в неинтерактивный режим, где нет ни меню, ни запроса кода.

Что стоит знать:

* **Вход проверяется в самом вебсокете.** `@app.middleware("http")` к вебсокетам
  не применяется — у них своя область запроса. Без явной проверки куки роут
  раздавал бы оболочку мини-ПК всем, кто дотянется до порта.
* **Сессия переживает обрыв.** Вывод копится в кольцевом буфере: уход во вкладку
  с кодом входа и возврат не теряют диалог.
* **Брошенная сессия живёт полчаса**, потом процесс гасится вместе со всей своей
  группой.
* **Windows не поддерживается** — там нет псевдотерминалов, а pywinpty ради
  случая, которого нет (локально есть обычная консоль), в зависимости не тянем.

Авторизация по-прежнему сохраняется в томе `factory-home`, то есть переживает
пересборку.

## Состояние машины

«Настройки → 📈 Машина»: загрузка процессора, память, диски, температура,
самые тяжёлые процессы.

Память показывается дважды намеренно. `/proc/meminfo` внутри контейнера отдаёт
цифры **хоста**, а лимит фабрики — три гигабайта из `compose.yml`. «Занято 2.9 ГБ»
в этих двух системах координат означает спокойный вечер и OOM через минуту
соответственно, поэтому рядом выводится и то и другое: второе читается из
`/sys/fs/cgroup/memory.max` и `memory.current`.

Температура берётся из `/sys/class/thermal` — внутри контейнера читается без
дополнительных прав и показывает нагрев хоста, что и требуется.

Список процессов обновляется в фоне и живёт пятнадцать секунд. Обход всех
процессов — единственная дорогая часть снимка: на рабочем ПК с четырьмя
сотнями процессов он занимает секунду, при том что всё остальное вместе
укладывается в шесть миллисекунд. Синхронный обход растянул бы на эту секунду
каждый ответ панели, а опрашивается она раз в три секунды.

## Автоархивы игр

Агент закончил работу — игра упакована. И после прогона студии, и после задачи
в чате.

```
studio_done / _on_chat_job_finished        игру убрали в архив
        │                                          │
        ▼                                          ▼
service.capture_build → builds.capture     archive.pack → builds.store_cold
        │                                          │
        ├── builds/<слаг>-ГГГГММДД-ЧЧММСС.zip      ├── zip_projects/<слаг>.zip
        └── строка в builds (без содержимого)      └── builds + build_chunks
                                                       (содержимое, до 128 МБ)
```

Решения и их причины:

* **Пакуются исходники, а не сборка.** `npm run build` после каждого прогона
  занимал бы минуты и падал бы чаще, чем срабатывал: игра в середине разработки
  собирается не всегда. Архив должен получаться всегда, иначе это не архив, а
  лотерея. Собранную версию по-прежнему делает кнопка на вкладке «Игра».
* **`.factory/` не попадает в архив.** Там теневой git-репозиторий снимков
  отката, и он бывает больше самой игры в разы.
* **Пустой архив не пишется.** У игры, уехавшей в холодное хранилище, остаётся
  каталог с одним `.factory/`. Zip из нуля файлов весит 22 байта и выглядит в
  списке настоящим — обманывая ровно того, кто полезет в него за игрой.
* **Эти архивы в базу не едут.** Только строчка в журнале. Заливать по два
  мегабайта через WAN после каждого прогона — это занятый канал ради истории,
  которая никому не нужна. Копию делает зеркало (ниже), раз в час.
* **В базу уезжает игра, отправленную в архив** (`ARCHIVE_TO_DB`, до 128 МБ).
  Вот там каталог удалён и zip остался единственным экземпляром — копия
  становится настоящей страховкой и способом забрать игру с другой машины.
  Возврат из архива копию убирает: слепок недельной давности под видом
  резервной копии хуже, чем её отсутствие.
* **Содержимое режется на куски по мегабайту.** Пакет крупнее
  `max_allowed_packet` сервер не отвергает с ошибкой, а рвёт соединение; предел
  на шаред-хостинге чужой и меняется без предупреждения.
* **Каталог `builds/`, а не `zip_projects/`.** В последнем наличие файла
  `<слаг>.zip` означает «игра убрана с диска» (`app/archive.py`) — экспорт туда
  соврал бы фабрике, что игры больше нет.
* **Хранятся последние десять на игру** (`BUILD_ZIP_KEEP`). Ночь автономной
  работы иначе оставляет сотню архивов одной игры.

Список и скачивание — «Настройки → 🗜 Хранилище → Архивы игр». Скачивание берёт
файл с диска, а если его там нет (фабрику развернули на другой машине) —
собирает из кусков в базе.

## Команды

```bash
cd /opt/zavod2

docker compose ps                        # состояние
docker compose logs -f factory           # логи фабрики
docker compose logs -f runner            # логи раннера
docker compose up -d --build factory     # пересобрать вручную
docker compose up -d --build runner      # обновить раннер (деплой его не трогает)

journalctl -u zavod2-deploy -f           # что делал автодеплой
systemctl status zavod2-deploy.path      # следилка за триггером
./docker/deploy.sh                       # деплой руками, без GitHub

systemctl status zavod2-tunnel           # туннель: сайт и MySQL
ss -lntp | grep 13306                    # проброс к базе жив?
```

## Зелёная галочка означает «обновилось»

Раньше не означала. Job в раннере умеет ровно одно — тронуть файл-триггер;
всё остальное делает systemd на хосте, вне GitHub. Значит и падение
происходило вне GitHub: деплой вставал на `git merge --ff-only`, а в Actions
горела зелёная галочка. Живой случай — мерж уехал в main, галочка зелёная, а
на экране фабрики полтора часа висела предыдущая версия.

Теперь `docker/deploy.sh` пишет исход обратно в тот же каталог, который видит
раннер (`.deploy` смонтирован ему как `/deploy`):

```
.deploy/status     sha, outcome, code, step, started, finished
.deploy/last.log   полный лог прогона
```

Исход пишется на **любом** выходе, включая падение по `set -e` и по сигналу:
запись только на успешном пути означала бы, что упавший деплой неотличим от
не начинавшегося, и job ждал бы его до таймаута.

Шаг «Дождаться деплоя» читает этот файл в цикле. Свой деплой он узнаёт двумя
способами: либо задеплоен ровно его коммит, либо успешный деплой стартовал
после его триггера — такой делал `git fetch` уже после пуша, значит коммит в
него вошёл (в main только fast-forward). Второй случай не теоретический:
`deploy.sh` догоняет пуши, прилетевшие во время сборки, и один прогон
закрывает сразу несколько.

Ждать при этом не значит молчать. Лог хоста пишется живьём в тот же каталог,
поэтому job транслирует его строками по мере появления — в Actions видно то же,
что видел бы человек у экрана мини-ПК. Опрос раз в три секунды: это чтение двух
коротких файлов.

Отдельно от лога хост объявляет текущий шаг (`.deploy/step`): `git fetch`,
`перенос игр из git`, `docker compose build` и так далее. Нужно там, где лог
молчит — docker тянет слои минутами, не печатая ни строки, и ожидание выглядит
зависшим.

При падении job дополнительно печатает хвост `.deploy/last.log`: `journalctl`
раннеру недоступен, а «деплой упал» без лога — сообщение ни о чём.

## Деплой не удаляет игры

Сгенерированные игры больше не едут в git. Сам по себе такой переход опасен:
merge стирает из рабочего дерева всё, что удалено во входящих коммитах, то
есть один пуш выносит всю папку игр на мини-ПК. Проверено на симуляции —
`git merge --ff-only` при чистом дереве удаляет игры молча и с кодом 0.

Поэтому перед merge, который удаляет файлы под `workspace/` или `output/`,
`deploy.sh` уводит эти папки в сторону обычным `mv` (переименование внутри
той же файловой системы — мгновенное и для гигабайта), проводит merge и
возвращает их на место уже нетрекаемыми. Возврат стоит в `trap`, поэтому
случается и при падении посреди процесса.

Побочный эффект, ради которого условие оставлено общим, а не одноразовым:
деплою вообще незачем уметь удалять игры. Игру удаляют кнопкой в фабрике, а
не пушем в main.
