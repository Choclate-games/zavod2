# Фабрика на мини-ПК: контейнер, вход, автодеплой

Рабочий ПК запускает фабрику локально (`python run_web.py`). На мини-ПК она
живёт иначе: в контейнере, за паролем и с автообновлением из `main`.

Этот документ — про второй случай.

## Что где

| | |
|---|---|
| Машина | мини-ПК `192.168.1.194`, пользователь `oem` (uid 29999) |
| Каталог | `/opt/zavod2` — обычный клон этого репозитория |
| Сайт | `http://192.168.1.194:7860` (после поднятия туннеля — `10.8.1.9`) |
| Контейнеры | `zavod2-factory`, `zavod2-runner` |
| Раннер | `minipc-zavod2`, метка `zavod2`, привязан к репозиторию |

Раннеры организации (`gh-runner-1`, `gh-runner-unity-1`) живут в другом
compose и про этот не знают: другие метки, другие контейнеры, другие тома.

## Вход

Фабрика запускает терминальных агентов и выполняет сгенерированный ими код.
Открытый интерфейс — это удалённое выполнение кода на машине, где рядом
работают раннеры организации, поэтому вход обязателен и включён по умолчанию.

Пароль хранится хешем, сессия — в подписанной куке:

```bash
python -m app.web.auth --hash    # спросит пароль, напечатает строку для .env
```

Строка кладётся в `AUTH_PASSWORD_HASH`. Смена пароля автоматически
разлогинивает все открытые сессии: ключ подписи кук выводится из самого хеша.

Отключается только для локального запуска на `127.0.0.1` — `AUTH_ENABLED=0`.
В контейнере это невозможно: `compose.yml` навязывает `AUTH_ENABLED=1` поверх
`.env`. При `AUTH_ENABLED=1` и пустом хеше сервер не поднимется вовсе — лучше
не запуститься, чем запуститься открытым.

Защита от перебора: десять неудачных попыток с одного адреса за пятнадцать
минут, дальше `429`. Счётчик в памяти, рестарт его обнуляет.

### Про `$` в `.env`

Docker Compose разворачивает `$` в значениях `env_file`. Если доллар окажется
внутри ключа, до контейнера доедет обрезанная строка, а compose ограничится
предупреждением `variable is not set`. Экранируется удвоением: `$$`.

Хеш пароля от этого защищён — в нём двоеточия, ровно по этой причине.

## Два файла с настройками

| Файл | Кому виден | Что внутри |
|---|---|---|
| `.env` | контейнеру фабрики | ключи провайдеров, пути, настройки входа |
| `.env.deploy` | контейнеру раннера | `GITHUB_REPO`, `GITHUB_PAT`, имя и метки раннера |

Разделение не косметическое. `.env` уезжает в фабрику целиком, а внутри неё
выполняется сгенерированный агентами код — токена с правами на запись в
репозитории организации там быть не должно.

На мини-ПК в `.env` переопределены пути (`/app/workspace`, `/app/output`
вместо путей Windows), выключены уведомления и задан `PREVIEW_HOST`.

## Как работает автообновление

```
push в main
   │
   ▼
workflow Deploy  →  раннер zavod2  →  тесты (389 шт.)
                                   →  самопроверка входа
                                   →  трогает /deploy/trigger
                                            │
                                            ▼
                              systemd zavod2-deploy.path (на хосте)
                                            │
                                            ▼
                              docker/deploy.sh: git merge --ff-only
                                               docker compose build factory
                                               docker compose up -d factory
```

Раннеру **не даётся** `/var/run/docker.sock`. Он не умеет ни собирать образы,
ни перезапускать контейнеры — только тронуть файл в bind-монте. Всё остальное
делает systemd от имени `oem`. Это сохраняет правило CI-инфраструктуры мини-ПК:
код из workflow не управляет демоном Docker хоста.

Несколько отдельных решений, каждое со своей причиной:

* **Регистрация на уровне репозитория, а не организации.** Org-раннер доступен
  всем репозиториям организации — job из любого из них выполнялся бы здесь.
* **Триггер только `push` в `main`.** Репозиторий публичный. `pull_request`
  означал бы выполнение кода с чужого форка на домашней машине.
* **`paths-ignore` на `workspace/` и `output/`.** Сгенерированные игры едут в
  git вместе с кодом, то есть коммит очередной игры — тоже push в `main`.
  Без фильтра фабрика перезапускала бы сама себя посреди работы.
* **`git merge --ff-only`, а не `reset --hard`.** В `workspace/` могут лежать
  ещё не закоммиченные игры. Деплой скорее встанет с внятной ошибкой, чем
  сотрёт их.
* **Деплой не трогает контейнер раннера.** Его перезапуск убил бы job, который
  этот самый деплой и запустил. Раннер обновляется руками:
  `docker compose up -d --build runner`.

## Что переживает пересборку

| Что | Где лежит |
|---|---|
| Игры (`workspace/`, `output/`, `zip_projects/`) | bind-монт в рабочую копию — оттуда же их забирает git |
| Авторизация всех шести агентов | том `factory-home` (`/home/factory`) |
| История расхода и квот | том `factory-state` (`/app/state`) |

История квот заслуживает пояснения. Модули `providers/agent_usage.py`,
`providers/agy.py` и `providers/quota_probe.py` ищут её по путям рядом с кодом:

```python
Path(__file__).resolve().parent.parent / ".agy_quota_history.json"
```

Путь захардкожен, переменной окружения нет — в контейнере это слой образа, и
история обнулялась бы на каждом деплое. `docker/entrypoint.sh` уводит эти
файлы симлинками в том. Работает потому, что все три модуля пишут через
`open(path, "w")`, то есть в существующий файл по ссылке.

## Авторизация агентов

Ставится один раз, живёт в томе `factory-home`:

```bash
docker compose exec factory claude      # дальше по ссылке в браузере
docker compose exec factory codex
docker compose exec factory opencode
docker compose exec factory agy
```

## Предпросмотр игр

`app/game_runner.py` поднимает dev-сервер игры и отдаёт браузеру адрес. На
одной машине это `localhost`; на сервере — нет, потому что «localhost» в
браузере пользователя это его собственный компьютер.

Поэтому адрес прослушивания и адрес для браузера разведены:

| Переменная | На мини-ПК | Зачем |
|---|---|---|
| `PREVIEW_BIND` | `0.0.0.0` | где слушает vite внутри контейнера |
| `PREVIEW_HOST` | адрес мини-ПК | что подставляется в ссылку |
| `PREVIEW_PORT_MIN/MAX` | `5100`/`5109` | контейнер публикует только заранее заданные порты |

При локальном запуске переменные не заданы и поведение прежнее.

**Важно:** dev-серверы игр за формой входа не стоят — это отдельные процессы
vite на своих портах. Ограничивать доступ к ним нужно файрволом.

## Команды

```bash
cd /opt/zavod2

docker compose ps                        # состояние
docker compose logs -f factory           # логи фабрики
docker compose logs -f runner            # логи раннера
docker compose up -d --build factory     # пересобрать вручную
docker compose up -d --build runner      # обновить раннер (деплой его не трогает)

journalctl -u zavod2-deploy -f           # что делал автодеплой
systemctl status zavod2-deploy.path      # следилка за триггером
./docker/deploy.sh                       # деплой руками, без GitHub
```
