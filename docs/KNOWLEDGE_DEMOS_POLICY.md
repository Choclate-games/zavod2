# 📋 Регламент: обязательное интерактивное демо для каждого знания (`knowledge/`)

Каждый файл в `knowledge/` — авторитарный источник для кодовых агентов фабрики.
Чтобы в базу не попадал «бумажный» код, действует жёсткое правило.

---

## 🎯 Правило «Knowledge + Working Demo»

1. **Никакого кода без проверки.** Новый рецепт, механика, контроллер или модуль в
   `knowledge/` обязан сопровождаться работающей вкладкой в
   `workspace/knowledge-showcase/`. Теоретический код без демо не принимается.
2. **Критерии качества демо** (эталон — вкладка «🚚 ЗиЛ-130»):
   * запускается через `npm run dev` без ручных шагов;
   * управление отзывчиво, есть визуальный **и** звуковой отклик;
   * на экране показаны горячие клавиши и одна строка о том, что демонстрируется;
   * работает на телефоне (тач-управление) или явно помечено как desktop-only;
   * код демо и код в `knowledge/` **совпадают**: демо — это тот же рецепт, а не
     «похожая» реализация.
3. **Стек демо — стек фабрики.** Демо пишутся на Three.js и библиотеках из
   `knowledge/stack/README.md`. Самописные аналоги того, что закрывает стек, в демо
   запрещены так же, как и в играх.

## Головная проверка вместо «посмотреть глазами»

Демо доказывает, что рецепт **играется**. Что он ещё и **считается верно**, доказывает
головной прогон без рендерера (`CRITICAL_RULES` §66). Каждая игровая механика в демо
живёт в модуле, не импортирующем `three`, и покрыта скриптом:

| Скрипт | Что проверяет |
|---|---|
| `npm run check:fighting` | фрейм-дата: наказуемость, затухание комбо, hit-stop, цепочки отмен, зоны и выносливость |
| `npm run check:fighting-sim` | прогон живого матча 90 с: идут ли попадания, не машет ли бот вне досягаемости, случился ли нокдаун, падает ли рэгдолл и встаёт ли боец с настила, работает ли перепрыгивание соперника, не копятся ли физические тела |
| `npm run check:racing` | геометрия трассы, 3 круга ботом, границы резинки |
| `npm run check:td` | 20 волн, приоритет целей, броня, экономика |
| `npm run check:rts` | флоу-филд через стену, слоты строя, таблица урона |
| `npm run check:survivor` | кривая опыта, пул карточек, баланс забега на 20 минут: держит ли игрок орду на 1/5/12 минуте |
| `npm run check:stealth` | конус зрения, шкала подозрения и grace period, радиусы шума, бюджет рейкастов |
| `npm run check:melee` | связка и окна отмены, буфер ввода, окна парирования, сектор поражения, физика рэгдолла на настоящем Rapier |
| `npm run check:building` | привязка к сетке, валидация постройки, снос и возврат ресурсов, BFS-энергосеть, обход преград |
| `npm run check:buoyancy` | сила Архимеда и равновесие, градиент нормалей волн, тепловой цикл и клин бура, разрушение пород и пул обломков |
| `npm run check:procedural` | генерация стилизованных 3D-моделей, BoundingBox, анимация походки, бенчмарк времени сборки (< 0.1 мс) |
| `npm run check:ortho2d` | ортокамера с фиксированной высотой мира 20, свайп-слайсер, провисание кривой Безье, граф дедукции улик |
| `npm run check:vfx` | пул 1000+ частиц без аллокаций, затухание масштаба, квадратичный отклик и спад травмы камеры |
| `npm run check:audio-rhythm` | аппаратные доли такта, окна точности PERFECT/GOOD/MISS, множители комбо, Dual Mute Gate |
| `npm run check:fight-anim` | анимации бойца: целостность запечённого мокапа, позы в живой игре (достаёт ли джеб, приседает ли присед, гнётся ли колено и в ту ли сторону, идёт ли удар рукой вперёд, а не вбок, доходит ли стопа удара ногой до своего хитбокса и заносится ли нога перед ударом), качество нокдауна (тело вытягивается, ложится, не проваливается сквозь настил, колено не выгибается), свежесть библиотеки `assets/proc_anim/` |
| `npm run check:fight-input` | раскладка файтинга в настоящем браузере: правая кнопка бьёт, а не открывает меню, `Ctrl` доходит до обработчика, каждая кнопка даёт заявленный приём, подписка снимается при уходе с вкладки (собирает `dist/`, поэтому вне `check:all`) |
| `npm run check:smoke` | дымовой прогон всех 15 демо без WebGL: сценарии ввода, исключения и NaN в трансформах |
| `npm run check:all` | всё сразу; входит в `npm run build` |

Эти прогоны уже поймали четыре бага, невидимых на глаз: сопротивление воздуха считалось
«за кадр» вместо «за секунду» (машина упиралась в 44 км/ч), очередь флоу-филда молча
переполнялась (юниты застревали посреди карты), и таблица урона RTS не была замкнутым
циклом (авиацию не бил никто). Четвёртый нашёл дымовой прогон: `MemorySystem.getRecord()`
в Yuka возвращает `undefined`, пока не вызван `createRecord()`, и охранник падал при
первом же обращении к памяти. Пятый нашла проверка слэшера: память связки тратилась
каждый кадр, поэтому длинный финишный удар съедал окно сам собой и третий удар связки
было невозможно собрать — на экране это выглядело как «иногда не выходит».

Шестой поймала проверка баланса survivor: здоровье врага росло множителем 1.55 за
минуту, и это давало спираль смерти — игрок переставал убивать, значит переставал
получать опыт и карточки, и его урон замирал навсегда, пока орда продолжала расти.
На экране это выглядит как «игра резко стала невозможной», причину не видно.

Седьмой, восьмой и девятый нашла проверка анимаций бойца, и все три —
**визуальные баги, которые числа проходили**. Колени были выгнуты назад в
девяти анимациях из двадцати: у бедра и голени перепутан знак поворота, но
поза от этого осталась похожей на правильную — присед приседал, прыжок
поджимал ноги, высота головы и размах стопы сходились. В рэгдолле руки и
ноги не были сшиты с телом (три сустава на восемь тел) — корпус падал, ноги
стояли. А темп шага крутился временем, а не расстоянием: цикл занимал 1.4 с,
за которые боец проезжал семь метров, и это читалось как «персонаж еле-еле
переставляет ноги».

Десятый нашла та же проверка, но уже у ударов ногами: хайкик задумывался в
голову, хитбокс стоял на 1.5 м, а поза доносила стопу до 1.33 — коробка била
выше собственной ноги. Замер тут формулируется как «стопа внутри хитбокса
своего же приёма», и правильным ответом оказалось опустить коробку, а не
дотянуть позу.

Одиннадцатым и двенадцатым оказались удар ногой и нокдаун — оба «работали»
и оба выглядели плохо, что и было единственным симптомом. Удар ногой вёлся
одной дугой синуса на весь приём, поэтому бедро поднималось одновременно с
выпрямлением голени: в кадре получался выпад, а не удар. Нокдаун собирал
рэгдолл из восьми тел с цельными руками-досками и шаровыми суставами без
пределов, а импульс получала одна кость из восьми — боец оседал вертикально
и превращался в комок на месте.

Оба случая одинаково поучительны тем, **как** их пришлось ловить. «Приём
проигрался» и «рэгдолл создался» верны в обоих случаях. Работающие замеры
получились такими: у ноги — сравнить сгиб бьющей голени до кадра попадания
и в нём самом (у выпада эти числа совпадают, у удара различаются вдвое); у
нокдауна — разброс тела по горизонтали (лежащий человек длиннее метра, куча
короче 0.8 м), высота головы в последнем кадре рэгдолла (лежит 0.25 м,
сидит 0.9 м) и нижняя точка коллайдеров.

Тринадцатым стал апперкот, и он же — лучший пример того, зачем мерить
направление, а не только величину. Запечённый мокап считает локальный
поворот сустава как «родитель⁻¹ × мировая цель», то есть предполагает, что
в игре родитель встанет как у актёра. Для таза это неверно: тазом
распоряжается игра, мокапный таз в неё не приезжает, и разница уходит в
плечо. В ударной стойке таз развёрнут боком — апперкот выносил перчатку на
**57 см вбок при 29 см вперёд**, то есть боец бил мимо соперника, а
проверка «перчатка ушла вперёд от стойки» всё это время проходила.

Отсюда правило для замеров позы: **проверяйте физический факт, а не «поза
изменилась»**. «Голова опустилась на 30 см» проходит и с вывернутыми
коленями; «колено впереди прямой бедро→лодыжка» — нет. Тот же принцип для
физики: не «рэгдолл создался», а «связей на одну меньше, чем тел» и «стопа
уехала вместе с тазом».

## Картинка — тоже проверка: витрина анимаций

Головной прогон ловит числа, но не ловит вид. Поэтому у файтинга есть
отдельная страница `anim.html`: по шесть кадров на каждую анимацию одним
листом, `npm run shots:anim` снимает листы через Playwright, человек их
смотрит. Три требования, без которых витрина врёт:

1. **Анимация вызывается нажатием тех же клавиш, что нажмёт игрок**, а не
   установкой состояния снаружи. Мы начали со второго, и витрина честно
   показывала стойку под подписью «шаг»: игровая логика каждый кадр
   переустанавливает состояние по вводу и затирала подставленное.
2. **Список анимаций — один на всех.** Витрина и генератор библиотеки берут
   его из одного модуля (`src/game/fightAnimStates.ts`), иначе картинка
   «всё нормально» относится к одному набору поз, а в игру уезжает другой.
3. **Состояния, которые не анимация, тоже снимаются.** Нокдаун — физика, в
   библиотеку клипов его не выгрузить, но ломается он так же молча и в кадре
   виден мгновенно. Он идёт отдельной полосой. Именно по этой полосе стало
   видно, что рэгдолл оседает кучей: головные замеры на тот момент говорили
   «все части сшиты, голова упала, ноги едут вместе с телом» — и все три
   были правдой.

Вкладкам со сложной анимацией стоит повторить этот приём.

## Убедитесь, что «до» — это действительно «до»

Отдельный пункт, потому что ошибка стоила почти правильного решения. Правку
ретаргета проверяли так: спрятать изменения через `git stash`, пересобрать,
замерить, вернуть. Числа совпали до сотых, вывод был «правка ничего не
меняет», и её чуть не выбросили.

`git stash` по умолчанию **не трогает неотслеживаемые файлы**, а скрипт
запекания в тот момент ещё не был закоммичен. Обе половины замера сняли с
одного и того же кода. Настоящее сравнение показало рост выноса на 15–25 %
у всех ударов и вдвое у апперкота.

Правило: перед сравнением «до/после» убедитесь, что «до» отличается от
«после» — хотя бы `git status` и одной строкой в выводе. Совпадение чисел до
сотых на физической симуляции с `Math.random()` в импульсе — это не
результат, это подозрение.

## Ввод мышью проверяется только в браузере

Таблица «кнопка → приём» проверяется головно, как фрейм-данные, — это
вопрос баланса (`fighting_game_core.md` §5а). Но между таблицей и игроком
лежит слой, которого в головном прогоне физически нет, и ломается именно он.
Поэтому у файтинга есть `check:fight-input`: Playwright открывает вкладку
кликом по карточке каталога, шлёт по канвасу настоящие `pointerdown` с нужной
кнопкой и `ctrlKey` и читает из HUD, какой приём пошёл у бойца.

Он сразу поймал две вещи, которых с головного прогона не видно. Первая:
`setPointerCapture` кидает `NotFoundError` на указателе, который браузер не
считает активным, и **обрывал весь обработчик до удара** — на живой мыши это
всплывает как «иногда клик не срабатывает». Отсюда порядок: подписчиков
вызывать первыми, захват — в `try`. Вторая: правая кнопка без
`preventDefault` на `contextmenu` открывает системное меню поверх канваса, и
сильный удар превращается в «Сохранить изображение как…».

Три вещи, которые такая проверка обязана делать:

1. **Сбрасывать состояние перед каждым нажатием.** Бот бьёт в ответ, и к
   третьему замеру игрок стоит в стане — кнопка честно не делает ничего, и
   проверка меряет ход матча, а не раскладку.
2. **Опрашивать результат, а не читать один раз.** Приём живёт свои кадры;
   «посмотреть через полсекунды» показывает уже следующее состояние.
3. **Проверять уход с вкладки.** Если подписка не снялась, клики продолжают
   бить в невидимого бойца поверх чужого демо.

Чего в браузерную проверку класть не надо — того, что зависит от хода матча.
Связка проверяется головно на `resolveCancel`, где попадание задано: в
браузере тот же замер зависел бы от того, дошёл ли удар до бота.

**Пустой прогон ничего не доказывает.** Дымовой прогон умеет держать кнопку и нажимать
клавиши (`Script` в `smoke-check.ts`) — без этого слэшер прогонялся зелёным просто
потому, что игрок ни разу не атаковал, и ветки «смерть врага → рэгдолл → новая волна»
не выполнялись ни разу. Добавляя демо в прогон, проверьте, что интересные ветки
действительно исполняются, а не только `init`.
