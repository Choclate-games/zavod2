# Готовые модели и чужой мокап в игре на Three.js: FBX, риг, ретаргет

> 💡 **Интерактивное демо**: `workspace/knowledge-showcase/` (вкладка *«🥊 Файтинг:
> фрейм-дата»*) — бойцы это X Bot и Y Bot из `assets/`, движения — 40 клипов из
> `assets/fight_anim/`. Код: `src/world/mixamoRig.ts` (загрузка, нормализация,
> риг), `scripts/bake-fight-anim.ts` (ретаргет мокапа), `src/world/fightClips.ts`
> (смешивание с позой-целью), `src/world/boxerRagdoll.ts` (рэгдолл из костей),
> `src/demos/FightingDemo.ts` → `poseRig()`.

Общая библиотека завода лежит в `assets/` (см. `assets/README.md`). Этот файл —
о том, **как превратить чужой FBX в управляемого персонажа**: не «загрузить и
показать», а вписать в игру, где уже есть своя анимация, своя физика и свои
головные проверки.

## 0. Готовая модель или риг из боксов

| | Готовая модель (этот файл) | Риг из боксов (`procedural_character_rig.md`) |
|---|---|---|
| Силуэт | человек сразу, без работы | читается человеком только после тюнинга |
| Кастомизация | цвет материала; лицо/телосложение — новая модель | цвет, лицо, телосложение, износ — параметрами |
| Вес билда | 1.5–2 МБ на модель | 0 байт |

Смешивать можно: демо файтинга держит оба рига за одним интерфейсом

загрузилась. **Вкладка стенда обязана открываться без ассетов** — файл могут
не докопировать в билд, и это не повод показывать чёрный экран.

## 1. Путь ассета в игру

Vite отдаёт только то, что лежит в корне проекта, поэтому нужный файл
копируется из `assets/` в `public/models/` игры. Дальше — обычный `FBXLoader`:

```ts
import { FBXLoader } from 'three/examples/jsm/loaders/FBXLoader.js';

const root = new FBXLoader().parse(bytes, '');   // parse, а не load
```

`parse(ArrayBuffer)` вместо `load(url)` — потому что байты в головной проверке
приходят из `fs`, а в браузере из `fetch` (§7). Один и тот же url грузится
один раз и кешируется: два бойца — это `SkeletonUtils.clone()` одного
источника, а не две загрузки.

## 2. Нормализация: четыре вещи, без которых модель ведёт себя странно

**Сантиметры.** Mixamo экспортирует рост ≈ 180 единиц. Масштаб **нельзя**
вешать на корневой узел: анимация двигает узлы в метрах (`body.position.y -=
0.2`), и внутри узла с `scale = 0.01` это превратится в 2 мм. Масштабировать
надо данные — вершины и локальные позиции костей:

```ts
const s = TARGET_HEIGHT / (box.max.y - box.min.y);
for (const b of bones) b.position.multiplyScalar(s);
for (const m of meshes) m.geometry.scale(s, s, s);
```

**Перепривязка скелета.** После масштабирования обратные матрицы костей
(`boneInverses`) считают старую бинд-позу. Пересчитать их надо **на месте**:

```ts
m.skeleton.calculateInverses();
m.bind(m.skeleton, m.matrixWorld.clone());
```

Соблазн собрать новый `new THREE.Skeleton(allBones)` — самая дорогая ошибка в
этой теме: атрибут `skinIndex` адресует кости **по порядку в скелете меша**, и
другой порядок молча привязывает живот к предплечью. Модель при этом не падает
и не ругается — она просто разъезжается, и выглядит это как «сломалась
физика».

**Кеш габаритов.** `Box3.setFromObject` кеширует `boundingBox`/`boundingSphere`
скиненного меша. Если посчитать его ДО масштабирования (а посчитать надо —
из него берётся `s`), кеш останется в сантиметрах навсегда. Сбрасывать явно:
`m.boundingBox = null; m.boundingSphere = null;`.

**Отсечение по фрустуму.** `frustumCulled = false` на скиненных мешах.
Сфера отсечения считается по бинд-позе; как только кости уезжают далеко
(рэгдолл, §5), персонаж исчезает ровно в тот кадр, когда на него смотрят.

## 3. Скелет Mixamo: что нужно знать до кода

* Имена — `mixamorigHips`, `mixamorigSpine`, `mixamorigSpine1/2`,
  `mixamorigNeck`, `mixamorigHead`, `mixamorig{Left,Right}{Shoulder,Arm,ForeArm,Hand}`,
  `mixamorig{Left,Right}{UpLeg,Leg,Foot,ToeBase}`. Двоеточие из `mixamorig:Hips`
  загрузчик срезает.
* Модель смотрит в **+Z**, стоит в T-позе, начало координат между ступнями.
* Иерархия — одно дерево из `Hips`: и ноги, и корпус висят на тазу.
* Локальные оси костей **не совпадают** с осями персонажа: у руки «вдоль
  кости» — это мировой X, у ноги — минус Y. Крутить кость напрямую («поверни
  локоть по X») нельзя, получится случайная ось.
* `Left*` — это сторона **+X**. Если ваша анимация зовёт «левой» переднюю руку
  в стойке, сверяйтесь со знаком координаты, а не с именем: мапинг по имени
  зеркалит стойку, и удары идут не с той стороны.

## 4. Как надеть анимацию, написанную кодом, на чужой скелет

Задача: не переписывать анимацию под скелет, а привести скелет к тому виду,
которого анимация ждёт. Между родителем и костью вставляются три узла:

```
parent → pivot → driver → aim → bone
         ^        ^        ^
         |        |        └ поза покоя: доворот кости в стойку
         |        └ его крутит анимация; оси = оси персонажа
         └ гасит мировой поворот родителя
```

```ts
const restWorld  = worldQuat(bone);
const parentWorld = worldQuat(bone.parent);
// направление «на ребёнка» → нужное направление в покое
const rotate = new THREE.Quaternion().setFromUnitVectors(dirToChild, DOWN);

pivot.position.copy(bone.position);
pivot.quaternion.copy(parentWorld).invert();   // оси driver = оси персонажа
driver.quaternion.identity();                  // ← сюда пишет анимация
aim.quaternion.copy(rotate);
bone.position.set(0, 0, 0);
bone.quaternion.copy(restWorld);
```

Три правила, каждое из которых стоило поломанной позы:

1. **`aim` — НИЖЕ `driver`, а не выше.** Если доворот вкрутить в `pivot`,
   вместе с костью развернутся и оси анимации: у руки, опущенной из T-позы
   поворотом вокруг Z, «вперёд» станет «вверх», и локоть сложится наружу.
   Со стороны это выглядит как гард наизнанку — при том, что числа стойки
   правильные.
2. **Суставы вставляются сверху вниз.** `pivot` считается по мировой матрице
   родителя; если начать с локтя, он прицелится к ещё неповёрнутому плечу.
3. **Направление покоя — то же, что в вашем риге.** Конечности вниз (`0,-1,0`),
   позвоночник вверх (`0,1,0`). После этого `driver.rotation.x = -0.78`
   означает ровно то же, что означало у процедурного рига, и вся фрейм-дата,
   дуги ударов и позы подъёма переезжают без правок.

Скручивание вокруг самой кости кратчайшая дуга не задаёт. Для рук в перчатках
и ног в ботинках это не видно; если видно — добавьте явный доворот в `aim`.
Отдельно предупреждение: «удар уходит вбок» — это НЕ про скручивание, сколько
бы ни было похоже. Причина другая и живёт в §6, ловушка №4.

**Что «оси = оси персонажа» означает для знака.** Приятное следствие: числа
из процедурного рига переезжают как есть. Неприятное: вместе с ними переезжает
и ошибка в знаке, если она там была, — и на скиненной модели она видна, а на
коробках не была. Конечность в покое смотрит в −Y, персонаж — в +Z, поэтому
`driver.rotation.x > 0` **уводит конечность назад**: колено вперёд — это
минус у бедра, пятка к ягодице — плюс у голени. Проверяется одним замером
(вынос колена вперёд от прямой бедро→лодыжка), подробности и формула — в
`procedural_character_rig.md` §6.

**Структура важнее имён.** Скелет Mixamo — одно дерево из таза, а анимация
обычно считает таз и корпус разными узлами (один опускает ноги в приседе,
другой наклоняет корпус в уклоне). Если оставить как есть, поза нокдауна
складывает оба смещения и боец уезжает под пол. Ноги переносятся под
отдельную группу (`hips.attach(legPivot)` — `attach`, а не `add`, чтобы
сохранить мировое положение), таз остаётся в корпусе.

**Аксессуары крепите к `driver`, а не к кости.** У драйвера оси персонажа и
известное направление покоя, поэтому «перчатка на запястье» — это
`(0, -длина_предплечья, 0)`, без разбора локальных осей кисти. Перчатку
сажайте на **середину кисти** и делайте длиннее неё: из коробки по размеру
запястья торчат пальцы, и в кадре видно только их.

## 5. Рэгдолл из скиненной модели

Работает — и выглядит лучше подмены на капсулы, потому что падает та же
модель, которая дралась. Три отличия от рэгдолла процедурного персонажа:

**Габариты костей приходится задавать.** `Box3.setFromObject(bone)` пустой: у
кости нет геометрии, меш один на всё тело. Считайте коробку по отрезку
скелета — от сустава до сустава плюс толщина:

```ts
target.setFromPoints([worldPos(joint), worldPos(childJoint)]).expandByScalar(half);
```

В демо это необязательное поле `RagdollBone.worldBox`: процедурный риг его не
задаёт и меряется по мешам, скиненный — задаёт.

**Кости можно переносить в физические тела.** `holder.attach(bone)` уводит
кость из скелетной иерархии, и скиннинг при этом не ломается: `Skeleton`
читает `bone.matrixWorld`, а не «кто чей родитель», а `bindMode: 'attached'`
(по умолчанию) каждый кадр пересчитывает `bindMatrixInverse` по мировой
матрице меша. Сам `SkinnedMesh` остаётся на месте в графе сцены.

**Отрезок берётся от сустава до сустава, а не от плеча до кисти.** Соблазн
описать руку одной коробкой велик — костей меньше, тел меньше. Но такая
рука не гнётся в локте нигде, и в падении это доска. Разбивайте по тем же
суставам, по которым разбита анимация: плечо→локоть, локоть→кисть,
бедро→колено, колено→стопа. Двенадцать тел вместо восьми — это разница
между сбитым человеком и манекеном из палок; числа и остальные ловушки —
`mechanics/ragdoll.md`, раздел «Почему рэгдолл выглядит кучей тряпья».

### Аксессуары: сравнивайте с головой

Перчатки, капа, шлем — это меши, которых в модели нет и которые приходится
дописывать. Две ловушки, обе стоили кадров.

**Размер берётся от модели, а не «на глаз».** Первая версия перчатки была
коробкой 0.15 × 0.21 × 0.17 — размером с голову бойца, и в кадре это
читалось как два синих ящика, летающих рядом с руками. Правильная опора —
кисть самой модели: у Mixamo её длина меряется обходом костей от запястья
до дальнего потомка (у меша один общий `Box3` на всё тело, отдельной кисти
в нём нет). Хорошая проверка на глаз — сравнить с головой: боксёрская
перчатка примерно вдвое меньше неё по каждой оси.

**Масштаб задаётся геометрии, а не мешу.** `mesh.scale` почти всегда уже
кем-то занят — у нас это squash & stretch на выпаде. Любой неединичный
базовый масштаб он затирает, и перчатка на первом же ударе становится
шаром. `geometry.scale(x, y, z)` при сборке этой проблемы не создаёт.

Возврат из рэгдолла — снимок локальных трансформов при сборке рига и
восстановление по нему (`boneRest`), иначе `add()` оставит кость с матрицей от
holder-группы. Подробности и фаза подъёма — `procedural_character_rig.md` §5.

## 6. Мокап на чужом скелете: ретаргет по направлениям

В `assets/x_bot` и `assets/y_bot` клипов нет — только техническая дорожка
`mixamo.com` в один кадр. Проверить это в любом FBX — одна строка:

```ts
console.log(obj.animations.map((a) => `${a.name} ${a.duration.toFixed(2)}s ${a.tracks.length}`));
```

Дорожка короче ~0.1 с — это T-поза, а не анимация.

Клипы приходят отдельно (`assets/fight_anim/` — 40 боевых движений), и почти
никогда — на том же скелете. В нашем наборе: кости `Spine1 / Chest / Neck1 /
LeftArm` вместо `mixorig*`, 76 костей вместо 129, и **rest-поза — боевая
стойка, а не T-поза**.

Отсюда правило: **не пытайтесь совместить скелеты, совместите движение.**

* Переименование костей не работает: одинаковое имя не значит одинаковые оси.
* Обычный дельта-ретаргет (`поворот в кадре` минус `поворот в rest`) не
  работает, когда rest-позы разные: у источника вычитается стойка, у цели
  прибавляется T-поза, и боец начинает клип, растопырив руки.
* `SkeletonUtils.retargetClip` — это тот самый дельта-ретаргет; он хорош,
  когда оба скелета в T-позе, и бесполезен здесь.

Работающий способ — **ретаргет по направлениям**. Для каждого кадра берём
мировое направление сегмента источника (плечо → локоть) и решаем поворот
своего сустава так, чтобы его кость смотрела туда же:

```ts
// сверху вниз: ребёнок считается по уже выставленному родителю
const dir = worldPos(src, 'RightForeArm').sub(worldPos(src, 'RightArm')).normalize();
const want = new THREE.Quaternion().setFromUnitVectors(REST_DIR, dir);  // REST_DIR = (0,−1,0)
driver.parent.updateWorldMatrix(true, false);
const parent = new THREE.Quaternion().setFromRotationMatrix(driver.parent.matrixWorld);
driver.quaternion.copy(parent).invert().multiply(want);
```

Это работает с любым скелетом, где можно назвать пары «сустав → ребёнок», и
не зависит ни от осей, ни от rest-позы. Три места, где он всё же ломается:

1. **Скручивание не переносится.** Кратчайшая дуга не задаёт поворот вокруг
   самой кости. Для рук в перчатках это не видно. Для **торса и головы —
   видно сразу**: плечи растут из груди, и ошибка в её скручивании уводит обе
   руки. Там ориентация решается полностью, по второй оси: для груди это линия
   плеч, для головы — линия глаз, для таза — линия бёдер.
2. **Опорная высота.** Смещение таза нельзя считать «относительно первого
   кадра клипа»: `get_up` и `knockdown_fall` начинаются лёжа, и боец получится
   лежащим на высоте стойки, а потом взлетающим. Отсчёт — от роста стоящего
   актёра, один эталон на весь набор.
3. **Разворот актёра.** Мокап записан в своей мировой ориентации; если игра
   тоже поворачивает бойца, повороты складываются. Гасится один раз по yaw
   таза в первом кадре.
4. **Родитель, которого в игре не будет.** Самая дорогая из четырёх, потому
   что ошибка получается тихой и красивой. Формула выше считает локальный
   поворот как `родитель⁻¹ · мировая_цель` — то есть предполагает, что в игре
   родитель встанет **точно так же, как у актёра**. Для таза это неверно по
   построению: тазом распоряжается игра (она поворачивает бойца к сопернику),
   и мокапный таз в неё не приезжает вовсе — он вне верхнего слоя.

   Разница между тазом актёра и тазом игры целиком уходит в плечо. А в
   ударной стойке таз развёрнут к сопернику боком, и угол этого разворота
   свой в каждом клипе и в каждом дубле. Замер в игре: апперкот выносил
   перчатку на **57 см вбок при 29 см вперёд** — боец бил мимо соперника, и
   ни одна проверка вида «перчатка ушла от стойки» этого не видела.

   Лечится двумя согласованными действиями на стороне запекания:

   ```ts
   // 1. Клип доворачивается так, чтобы сам удар смотрел в +Z.
   //    Опора — не таз, а самая вытянутая по горизонтали конечность.
   if (isStrike) correct.premultiply(yawTo(strikeDir, FORWARD));
   // 2. Таз в ЦЕПОЧКЕ решается без поворота вокруг вертикали — тогда рука
   //    считается относительно таза, смотрящего вперёд, как оно и будет.
   if (isStrike && key === 'body') want.setFromEuler(stripYaw(want));
   ```

   Стало: 62 см вперёд, 17 вбок. По остальным ударам вынос вырос на 15–25 %,
   и джеб перестал быть единственным, кому мокапной руки «не хватало».

   **Только для ударных клипов.** Отделить удар от неудара порогом
   вытянутости не выйдет: лежащий на настиле боец вытягивается не хуже
   бьющего (0.99 против 0.93 у бэк-кика). Признак другой — как игра
   пользуется клипом: если она берёт из него таз и ноги целиком, поворот
   таза там часть позы, и выпрямлять клип нельзя. Список таких клипов
   читается из самой таблицы применения, а не переписывается в пекарь
   руками.

### Запекание вместо загрузки FBX

40 клипов — это 26 МБ FBX, и в каждом ещё и скиненный меш, который игре не
нужен. Поэтому ретаргет — **шаг сборки**, а не работа в рантайме:
`npm run bake:fight-anim` читает FBX и пишет один файл с поворотами
драйверов (~700 КБ на 40 клипов при точности 0.001). В игре грузится только он.

Заодно на этом шаге чинится третья беда чужих клипов — **мусор по краям**.
Мокап-файл на 3–6 секунд содержит 0.5–1.5 с движения, остальное актёр стоит.
Окно ищется по энергии (сумма смещений кистей, стоп и головы по кадрам) с
порогом ~12% от пика; без обрезки каждый удар в игре начинался бы с паузы.

### Смешивание с позой-целью

Клипы редко закрывают весь набор состояний: в нашем наборе есть удары, блоки,
падения и подъём, но **нет стойки и шагов** — того, что боец делает большую
часть матча. Поэтому клип не заменяет позу-цель, а домешивается к ней
последним:

```ts
poseRig(f, dt);                       // сначала поза из фрейм-даты
applyClip(rig, use, progress, w);     // потом мокап тянет драйверы к себе
// внутри: target.quaternion.slerp(clipQuat, w)
```

Порядок даёт бесшовный выход: как только вес упал, экспоненциальное
приближение позы-цели доводит бойца до стойки **из той позы, где его оставил
мокап**. Вход — за 3–4 кадра, иначе на первом кадре приёма поза прыгает.

Вес меньше единицы — рабочий инструмент, а не компромисс: у нас присед из
мокапа опускает голову на 14 см, а игровой — заметно ниже (иначе непонятно,
почему удар прошёл над головой). Клип берётся с весом 0.5 ради формы рук,
глубину задаёт игра. Клипы, которые **ухудшают читаемость механики**, лучше
не брать вовсе: мокапные уклоны — это перенос веса на 3–7 см, и подмешивание
гасило игровой уклон.

### Слои: корень принадлежит игре

Самая дорогая ошибка при подмешивании мокапа — отдать клипу таз и ноги.

Мокап записан со своим движением корня: актёр шагает, приседает, переносит
вес. В игре корнем распоряжается совсем другой код — он держит бойца на полу,
сводит дистанцию, толкает откидыванием, поднимает в прыжке. Эти двое начинают
спорить, и выглядит это так: персонаж наклоняется вперёд всем телом, **стопы
отрываются от пола и висят**, колени доворачиваются туда, куда их вёл актёр.
На кадрах ударов у нас получился полёт в позе ныряльщика.

Поэтому клип берётся слоями:

## 6a. Мокап → ПРОЦЕДУРНАЯ анимация: ряды Фурье и ключевые позы

Ретаргет из §6 отдаёт клип: дорожки поворотов по кадрам, которые игра грузит
файлом и играет микшером. Для боевых связок это правильно. Для того, что
персонаж делает ВСЁ время — стоит, идёт, бежит, стреляет, получает пулю, —
клип оказывается неудобным и дорогим сразу с двух сторон.

**Дорого.** Пять клипов шутера — 2 МБ FBX (или ~200 КБ после запекания в
JSON). Это отдельный запрос, отдельное ожидание и отдельный риск, что ассет
не доедет.

**Неудобно.** У клипа своя длительность. Враг, идущий вдвое медленнее актёра,
требует `timeScale`, и всё равно ноги «едут» по земле: скорость персонажа
задаёт игра, а длина шага зашита в мокап. Наложить выстрел на бег — второй
микшер и ручное разведение слоёв.

Оба вопроса снимает одно преобразование: **клип не хранится, а
аппроксимируется**, и результат ложится числами прямо в исходник
(`src/world/shooterAnimData.ts` в стенде, генератор —
`scripts/bake-shooter-anim.ts`). 5.6 МБ FBX → 22 КБ TypeScript, который
жмётся gzip вместе с кодом.

### Циклы — рядом Фурье по фазе

Ходьба, бег и приставной шаг периодичны. Периодическая функция — это ряд:

```typescript
// v(φ) = a₀ + Σ aₖ·cos(kφ) + bₖ·sin(kφ)
function fourier(values: number[], harmonics: number): number[] {
  const n = values.length;
  const coef = [values.reduce((s, v) => s + v, 0) / n];
  for (let k = 1; k <= harmonics; k++) {
    let ac = 0, as = 0;
    for (let i = 0; i < n; i++) {
      const phi = (2 * Math.PI * k * i) / n;
      ac += values[i] * Math.cos(phi);
      as += values[i] * Math.sin(phi);
    }
    coef.push((2 * ac) / n, (2 * as) / n);
  }
  return coef;
}
```

Три гармоники дают 7 чисел на ось вместо 21 кадра, и ошибка подгонки на
реальном мокапе — **0.6° в среднем, 8° в пике** (пик приходится на момент
касания стопы, где кривая ломается). Это меряется в самом скрипте запекания
и печатается в консоль: подгонка без замера ошибки — это подгонка на глаз.

Два бесплатных следствия:

* **Шва нет.** Ряд периодичен по построению, последний кадр сходится с
  первым точно. У запечённого клипа шов приходится латать вручную.
* **Углы надо разворачивать до подгонки.** `Euler` из кватерниона прыгает
  через ±π, и один такой прыжок ряд размазывает по всему шагу «дрожью».
  Разворот — по предыдущему кадру:
  ```typescript
  while (v - prev > Math.PI) v -= 2 * Math.PI;
  while (prev - v > Math.PI) v += 2 * Math.PI;
  ```

### Фаза гонится ПУТЁМ, а не временем

Это то, ради чего всё и делалось. Скрипт запекания меряет длину шага
(максимальный разнос стоп вдоль направления взгляда), и в игре:

```typescript
const cyclesPerMeter = 1 / (clip.stride * 2);       // один оборот = два шага
phase += speed * dt * cyclesPerMeter * Math.PI * 2;
```

Ноги не едут ни на какой скорости, потому что скорость и длина шага — одна
и та же величина по обе стороны формулы. Никакого `timeScale`.

Скорость берётся из **разницы позиций**, а не из намерения ИИ: враг,
упёршийся в ящик, обязан перестать перебирать ногами.

### Одиночные движения — ключевыми позами и ДЕЛЬТОЙ

Выстрел, реакция на попадание, смерть — не циклы. Они хранятся 8–14
ключевыми позами с временами, между ними линейная интерполяция.

Ключевое решение — что именно хранить:

| Движение | Что хранится | Почему |
|---|---|---|
| Выстрел | дельта от стойки | иначе стреляющий на бегу замирает |
| Реакция на попадание | дельта от первого кадра клипа | подмешивается к любой позе |
| Смерть | абсолютная поза | у падения нет смысла «наполовину» |

Дельта реакции считается от **первого кадра самой реакции**, а не от стойки
целевого персонажа: у боевого набора rest-поза — боксёрская стойка, и
вычитание прицельной позы стрелка опустило бы врагу руки ровно в момент
попадания.

Огибающая одиночного движения — несимметричная:

```typescript
const p = t / duration;
return p < 0.18 ? p / 0.18 : 1 - (p - 0.18) / 0.82;   // резкий вход, долгий выход
```

Симметричный `sin(πt)` даёт «наплыв» вместо удара: реакция должна начинаться
в тот же кадр, что и попадание, иначе она читается как отдельное событие, а
не как следствие.

### Слои

```
стойка (ряд по времени, дыхание)
  → цикл хода (ряд по фазе, вес = скорость/макс)
    → + выстрел (дельта × огибающая)
      → + попадание (дельта × огибающая)
        → смерть перекрывает всё
```

Голова доворачивается на цель **кодом, поверх мокапа**: мокап не знает, где
игрок, а доворот головы — половина ощущения, что тебя видят.

### Обрезка и потолок длительности

Мокап-файл — это 3–6 секунд, из которых движения 0.5–1.5 с. Обрезка по
«энергии» (сумма смещений кистей и стоп по кадрам) снимает тишину в начале и
в конце. Но одной обрезки мало: `hit_react_face` — 4 секунды, где реакция
занимает полсекунды, а дальше актёр отыгрывает «приходит в себя». В бою
врагу столько думать нельзя, поэтому у одиночных клипов есть ещё и потолок
длительности (0.5–0.6 с для реакций).

### Реквизит — по двум кистям, а не на кости

Оружие в руках персонажа привязывают к кости кисти с фиксированным
смещением. Смещение подбирают под одну позу — и во всех остальных вторая
рука висит рядом с оружием. Именно это читается как «странно держит оружие».

Надёжнее ставить реквизит каждый кадр по обеим кистям:

```typescript
axis.subVectors(wristSupport, wristTrigger).normalize();   // вдоль ствола
up.set(0, 1, 0).applyQuaternion(chestWorldQuat);           // чтобы не крутилось
side.crossVectors(axis, up).normalize();
up.crossVectors(side, axis).normalize();
m.makeBasis(side, up, axis.clone().negate());              // ствол — локальная −Z
rifle.quaternion.setFromRotationMatrix(m);
rifle.position.copy(wristTrigger).addScaledVector(axis, -0.02);
```

Три детали, каждая из которых стоила кадра:

* **Начало координат модели — на рукояти**, и оружие ставится в ведущую
  кисть. Постановка в СЕРЕДИНУ между кистями сдвигает винтовку на полразмаха
  рук вперёд: ствол торчит далеко перед бойцом, приклад висит на второй руке.
* **Вертикаль берётся от груди.** Без неё оружие свободно вращается вокруг
  линии рук, и магазин в случайный момент смотрит вверх.
* **Всё это посчитано в МИРОВЫХ координатах, а `position` и `quaternion` у
  реквизита — ЛОКАЛЬНЫЕ.** Записать мировые числа в узел, висящий на
  повёрнутом и смещённом корне персонажа, — значит применить трансформ
  персонажа второй раз:

  ```typescript
  root.getWorldQuaternion(rootQ);
  rifle.quaternion.copy(rootQ.invert()).multiply(worldQ);
  rifle.position.copy(root.worldToLocal(worldP));
  ```

  Без перевода оружие улетает ровно на позицию персонажа от начала координат
  и парит над уровнем само по себе. Ловушка коварна тем, что **пока риг стоит
  в нуле, ошибки нет**: и юнит-тест, и скрипт запекания ставят персонажа
  именно туда, так что баг живёт только в игре. Проверка поэтому меряет не
  «оружие существует», а расстояние от ствола до груди хозяина.

> **Ось кистей — не ось прицеливания.** Ствол стоит по линии кистей, но в
> бладированной мокапной стойке эта линия уходит от «вперёд» модели на
> 40–60°, и развернуть персонажа лицом к цели — значит увести оружие мимо
> неё. Как это меряется и компенсируется — `shooter_enemy_ai_and_combat.md`
> §5a.

### Клон делит геометрию с оригиналом

`SkeletonUtils.clone` копирует кости и меши, но **буферы геометрии остаются
общими** с исходной моделью — на то и клон. Модель при этом обычно лежит в
кэше загрузчика и нужна другим сценам.

Отсюда правило уборки: перед общим обходом сцены с `geometry.dispose()`
персонажи снимаются со сцены и освобождаются своим методом, который трогает
только то, что риг создал сам (материалы, дописанное снаряжение). Иначе одна
закрытая вкладка убивает модель для всех, кто загрузит того же бота следующим,
— и симптом будет «персонаж не грузится», за много шагов от места аварии.

### Не всякий FBX прочитается

В наборе Shooter Pack пять файлов из шестнадцати загрузчик three не
разбирает — «Unknown property type». Формат у них тот же FBX 7700 с тем же
набором типов свойств, что и у читающихся: дело в загрузчике, а не в
ассетах. Вывод практический: **список клипов проверяется до того, как под
него написан рантайм**, и у каждого нужного движения должна быть замена в
том же или соседнем наборе.

## 7. Головные проверки: модель должна грузиться без браузера

`scripts/*-check.ts` гоняют игру без DOM и WebGL (`CRITICAL_RULES` §66). Если
проверка подсунет заглушку вместо модели, она будет мерить риг, которого в
игре нет. Поэтому чтение байтов — одна подменяемая функция:

```ts
let readBytes = async (url: string) => {
  if (typeof window !== 'undefined') return (await fetch(url)).arrayBuffer();
  // спецификатор из кусков: иначе Vite тащит node:fs в браузерный бандл
  const fs = await import(/* @vite-ignore */ `${'node:fs'}/promises`);
  return (await fs.readFile(new URL(`../../public/${url}`, import.meta.url))).buffer;
};
```

`FBXLoader.parse` в Node работает как есть — ни DOM, ни WebGL ему не нужны.
Что проверять на модели, а не на глаз:

* рост после нормализации равен ожидаемому (иначе хитбоксы мимо);
* мировые позиции ключевых узлов в стойке (перчатки у подбородка, а не у
  живота) — это ловит перепутанные оси драйвера;
* габариты коробок рэгдолла не нулевые и не в сантиметрах;
* живой матч: попадания идут, боец встаёт после нокдауна
  (`fighting_game_core.md` §10).
